0. GOAL, DESIGN PRINCIPLES, WHAT "DONE" MEANS
================================================================================
GOAL
  A generalist toolkit that lets you (a) translate a staff-analyst task into
  code quickly, (b) test and debug it without AI access, and (c) build
  intuition for analyses you have not run before — each template doubles as
  a worked lesson.

PRINCIPLES
  P1  Standalone templates. Each template folder runs with nothing but its own
      files + its requirements.txt. No template imports another template.
  P2  Copy, don't import. Shared helpers (synthetic data, schema checks) are
      COPIED into each template. Duplication is accepted on purpose; it is
      the price of P1.
  P3  Orchestrator is an observer. It discovers templates by folder
      convention and runs their tests in a subprocess. It never imports
      template code, and templates never reference it. Delete either side
      and the other still works.
  P4  Offline first. Every test runs on seeded synthetic data. Public-use
      files (PUFs) are documented and optional, never required, never
      committed (inherits TEST_DATA.txt governing rule).
  P5  Beginner-legible. Plain-English docstrings with numbered steps, worked
      examples, and "common mistakes" in every function.
  P6  Runnable at every stage. A freshly cloned template passes its contract
      tests before you write a single line (see Stub policy, 3.3).
  P7  Two languages of the job: Python for analysis, SQL "twin" files for the
      warehouse logic (run locally via DuckDB, no server needed).
  P8  Windows-native. pathlib everywhere, .bat + .sh launchers, VS Code
      test-explorer config included.

DONE MEANS
  - 16 templates, each: `python run.py` produces outputs; `python run.py
    --selftest` passes without pytest; `pytest` passes (xfails allowed only
    for marked TODO exercises).
  - `python orchestrator/run_all_tests.py` runs all 16, writes a summary
    table + JSON + HTML report, exits non-zero on any real failure.
  - Glossary HTML with ~31 niche workflows, each with a copy-paste block that
    runs standalone and self-tests.
  - This plan committed as IMPLEMENTATION_PLAN.txt at repo root.

3.2 DOCSTRING STANDARD (NumPy style + 4 beginner sections)
--------------------------------------------------------------------------------
  Summary line  -> one sentence, plain English
  Healthcare context -> why an analyst does this, who consumes it
  Parameters / Returns -> with column names and units

3.3 STUB POLICY (recommended "hybrid" — see Decision D1)
--------------------------------------------------------------------------------
  - CORE functions ship a minimal, correct baseline so run.py and contract
    + known-answer tests PASS on first clone.
  - EXTENSIONS are stubbed: body contains the numbered steps as comments
    and `raise NotImplementedError("TODO[L2]: ...")`.
  - Each extension has a test in test_exercises.py marked
    @pytest.mark.xfail(raises=NotImplementedError, strict=False).
    When you implement it the test turns XPASS -> you remove the marker.
  - The orchestrator reports PASS / FAIL / TODO(xfail) separately, so the
    summary doubles as a learning checklist.

3.4 TEST TIERS (per template)
--------------------------------------------------------------------------------
  contract     output shape/columns/dtypes                 always pass
  known_answer tiny hand-computed inputs                   always pass
  checks       injected defects trigger findings           always pass
  sql_twin     pandas == SQL (M-tier templates + T14)      always pass
  exercises    TODO extensions                             xfail until done
  selftest     same core asserts, plain `assert`, no pytest (run.py flag)
  Runtime budget: < 10 s per template, < 3 min for all 16.

3.5 DATA POLICY
--------------------------------------------------------------------------------
  - Only generated data is committed (tests/fixtures + tiny samples).
  - Synthetic realism rules (from TEST_DATA.txt): right-skewed cost with long
    tail, Dec/Jan seasonality, 3-month runout tail, 3–5% claim versions,
    1–2% overlapping enrollment spans, Luhn-valid NPIs, ZIPs with leading
    zeros, zero/negative paid lines.
  - Code values are FORMAT-valid, not clinically curated; clinical code
    lists used in measure logic are small illustrative excerpts and say so.
  - Any coefficient/weight table that is published by CMS or licensed
    (HCC coefficients, NCQA value sets) ships as a labeled FAKE toy table;
    README shows where to get the real one.

3.6 MOCK-UP OF ONE REAL FILE  (t05 .../pipeline/analyze.py, excerpt)
--------------------------------------------------------------------------------
def compute_member_months(enrollment: pd.DataFrame,
                          period_start: str,
                          period_end: str) -> pd.DataFrame:
    """Convert enrollment spans into prorated member-months per calendar month.

    Healthcare context
    ------------------
    PMPM = cost / member-months. The denominator must credit partial months
    fractionally: a member enrolled 15 of 31 days in January contributes
    15/31 = 0.484 member-months, not 1.0. Getting this wrong makes cost per
    member look lower than it is, which Finance will carry into a payor
    negotiation.

    Parameters
    ----------
    enrollment : DataFrame
        One row per enrollment span. Required columns:
        member_id (str), enroll_start_dt (date), enroll_end_dt (date,
        inclusive), lob_cd (str, e.g. 'MCD' Medicaid).
    period_start, period_end : str
        'YYYY-MM-DD' analysis window, inclusive.

    Returns
    -------
    DataFrame with columns member_id, month (Period[M]), lob_cd,
    member_months (float in (0, 1]).

    Steps
    -----
    1. Clip each span to [period_start, period_end].
    2. Explode each span into the calendar months it touches.
    3. For each month: days_enrolled = overlap(span, month) in days.
    4. member_months = days_enrolled / days_in_month.
    5. Sum by member_id, month, lob_cd (merges overlapping spans — see
       checks.check_overlapping_spans, which must run first).

    Example
    -------
    >>> e = pd.DataFrame({"member_id": ["A"], "lob_cd": ["MCD"],
    ...     "enroll_start_dt": pd.to_datetime(["2025-01-17"]),
    ...     "enroll_end_dt": pd.to_datetime(["2025-02-28"])})
    >>> compute_member_months(e, "2025-01-01", "2025-12-31")["member_months"].round(3).tolist()
    [0.484, 1.0]

    Common mistakes
    ---------------
    - Counting a member as 1.0 for any month they touch (inflates denominator).
    - Treating enroll_end_dt as exclusive (drops the last day).
    - Summing overlapping spans without de-duplicating (member_months > 1).

    TODO[L2]: add `mode="first_of_month"` for payers that credit a full
    month if enrolled on the 1st (a common contract convention).
    """

     actuarial opinion).
